# トークン使用量の調査と Claude・Codex 共創の改善案

作成日: 2026-10-25（日本時間）

## 位置付け

この文書は調査結果、現在の担当の申し送り、次の Bolt を検討するための提案である。現在の Intent、承認済み計画、検証コマンド、承認記録を変更するものではない。改善の実装は現在の Bolt のリリース・本番確認後に、別の Inception で範囲を決めて承認を得てから行う。

Codex 固有の設定や個人の会話履歴を前提にせず、Claude Code と Codex のどちらからも参照できる共通知識として保存する。文書の保存だけでは自動読み込みや設定変更は発生しない。

## 現在の担当と競合時の扱い

- ユーザーは、現在の U1 の実装を Claude 側で進め、Codex はトークン調査のみを行うと指定している。
- 現在の作業で成果物が競合する場合は Claude 側の判断・成果物を優先する。Codex は自分の版を復元したり、Claude の変更を取り消したりしない。
- Codex が今回保存するのは本ファイルだけとする。アプリケーション、承認済み設計・計画、共有の状態・監査記録、実行中のプロセス、既存の引き継ぎ文書は変更しない。
- ユーザーからの申し送りでは、U1 は「30秒待機上限の計画」が承認済み。本調査では計画本文を再読しておらず、その上限の対象や意味を再解釈しない。以下の将来提案によって現在の上限を変えない。
- Claude の優先は人間の承認を代行する権限ではない。承認記録や監査記録の整合性は公式コマンドで維持する。

### Codex が実行した停止操作の申し送り

調査後に自動継続メッセージが届き、Codex が `aidlc engine orchestrate park` を実行した。返答は `kind: parked`、対象は `code-generation` / `u1-company-notes` だった。

この操作は読み取り専用ではない。その後、`aidlc-orchestrate.ts` の実装コメントで、`park` がワークフローの `Parked` 状態を永続化することを確認した。セッション限定の停止として使わない。実行時点で Claude にどの影響が出たかは確認していない。Codex から復旧、再開、追加の停止操作は行わない。Claude 側で必要な場合に扱うため、実行事実をここに残す。

### 調査セッションへの自動継続も改善対象

調査文書の保存が終わり、実装に参加しないと明記した後も、この Codex セッションへ `u1-company-notes` の Code Generation を続ける自動メッセージが繰り返し届いた。このため、実装に関与しない調査セッションでも不要なモデル応答が発生した。ユーザーの新しい依頼や承認ではない。

その過程で Codex が起動した `aidlc engine orchestrate next` は結果を返さず、Codex 自身の当該コマンドだけを中断した。Claude 側のプロセスには操作していない。状態への影響を検証する目的で、追加の状態確認・変更を繰り返さない。

将来の改修では、進行担当のワークフローを停止せず、調査担当のセッションだけが正常に終了できることを受け入れ条件に含める。共有ワークフローの `park` やガード無効化を代替策にしない。現在、この分離が実装済みとは扱わない。

## 調査方法と範囲

- 保存済みのローカルセッション記録から、対象リポジトリの使用量メタデータとツール呼び出しを集計した。
- Codex は `token_count` の累計値を使用した。Claude は同じ応答の複数レコードを応答 ID 単位でまとめて使用量を集計した。
- 以下は確認したセッションの例であり、アカウント全体の網羅的集計ではない。複数セッションの累計を単純加算していない。
- 文書には元の会話、コード、ユーザー文書、秘密情報、機械固有のパスを転記しない。
- AI-DLC の Session Cost は工程数・所要時間などの集計であり、実トークン数の計測器ではない。

## 「毎回ログを読んでいるか」の結論

毎回作業ログ全文を読む動作は立証していない。Claude の上記セッションでは、監査パスへの参照を含むコマンドが3件、`memory.md` への参照を含むコマンドが1件あった。参照文字列の検出であり、全文を読んだか、必要な診断だったかまでは分類していない。

一方、短い間隔での待機確認の多さは Codex の記録で確認できた。文書の参照や読み取りを含む呼び出しも複数あったが、ファイル名の登場回数をそのまま再読回数として扱わない。

したがって、改善対象は「全ログを禁止する」ことではなく、状態が変わっていないのに読むこと、同じ版の資料を再投入すること、短い間隔でモデルを起こして確認することである。

## 原因の評価

1. **長い文脈と多い確認回数の組み合わせ: 強い候補。** ツール結果を受けてモデルが再び動くときにも、履歴や指示が入力になる。ファイルを再読しなくても累計入力は増える。
2. **モデル選択: Claude 側で改善余地あり。** 主会話は Opus だった。通常実装と難しい設計判断での使い分けは将来の検討対象。現在の実装途中では変更しない。
3. **補助エージェント: 追加消費はあるが、主因とは未確定。** 必要な公式レビューを消費削減だけの理由で省略しない。
4. **キャッシュ不足: 今回の Codex の主な例では説明しにくい。** キャッシュ率は高かった。高キャッシュ率でも大量の再処理があることに注目する。

OpenAI・Anthropic ともモデル、文脈、推論、キャッシュなどで消費が変わると説明している。生のトークン数だけから契約プランの5時間枠を正確に換算することはしない。Claude と Codex の使用量も同一の枠として足し合わせない。

## Bolt 間で検討する改善

### 読み直しと出力を減らす

- 同じ作業の同じ版の資料は、すでに取得した内容を利用する。再開時、変更の通知を受けたとき、失敗の診断時に必要箇所を読む。
- 通常の作業ループで監査ログ全体を読み込まない。監査調査を明示的に頼まれた場合に必要な範囲だけ読む。
- 直前のコマンドが状態の変化や結果を返した場合、その事実を知るためだけに別途状態ファイルを開かない。
- 長いテスト・ビルドの出力はファイルに保存し、失敗箇所と必要な末尾だけを取り込む。
- AI-DLC が返す必須の指示は切り詰めない。一度取得した指示を無意味に再取得しない。
- 必須の承認・再開確認・レビューの読取要件は維持し、必要な確認と惰性的な再読を区別する。

### 待機でモデルを何度も起こさない

- 実行開始時に、承認済みの制約とツールが許す範囲で十分な待ち時間を指定する。
- 完了通知が使える場合は通知を利用する。中身を確認しないまま短い待機を繰り返さない。
- 非同期実行の戻り値と実処理の完了を区別する。1〜10秒指定の確認を機械的に繰り返さない。
- 現在の U1 の30秒上限と、既存の待機規則・ツール制約の具体的な整合は、将来の計画で確認する。現在の計画に一律の新しい待機上限を持ち込まない。

### Claude と Codex が共通で使える共創方式

- **進行担当を1つにする。** 同じ Intent に対する状態遷移、承認の記録、実装の取り込みを担当するセッションを明示する。今回は Claude が担当する。
- **調査担当を分離する。** 調査側は対象を読むだけにし、単独の調査文書を所有する。調査中に `next`、`continue`、`report`、`park` を実行して進行へ参加しない。
- **担当交代を明示する。** 交代時に人間が進行担当を決め、未完了の操作、対象ファイル、確認済みの根拠、未解決事項を最小限で引き継ぐ。
- **文書形式を共通化する。** 担当、目的、対象、所有ファイル、基準となる版、結果、未解決事項を共通項目とする。どちらか片方にしか読めない会話メモを正本にしない。
- **同じファイルを同時に編集しない。** 将来、別作業を依頼する場合は所有ファイルまたは別の作業ツリーを分ける。現在は並列実装を始めない。
- **競合時に自動で書き戻さない。** 現在は Claude を優先する。Codex の未反映案は提案として残し、採用・取り込みを Claude に委ねる。状態・承認・監査記録をテキスト上書きで修復しない。
- **調査セッションを自動継続の対象から分離する。** 共有設定やガードを緩める方法ではなく、公式に対応するセッション単位の方法を調べる。今回の `park` の扱いも検証対象にする。

上記は実装案であり、共有ロックや両ツールの連携機能が既に動作しているという意味ではない。Claude Code 用・Codex 用の入口から同じ共通ルールを参照できる設計を目指す。

## 将来の受け入れ条件案

- 状態変化のない待機で、作業ログや同じ版の資料を再読しないことを、限定した実行サンプルで確認できる。
- 共通の短い作業例で、変更前後のモデル呼び出し数、入力、キャッシュ、出力、待機回数を比較できる。推定トークン数を使わない。
- 同じ Intent で一方が進行担当、他方が調査担当のとき、調査側が共有状態を進めたり停止したりしない。
- Claude Code と Codex の両方で、担当の確認・引き継ぎ・独立文書の保存を同じ手順で実施できる。
- 人間の承認ゲート、TDD、必要なレビュー、検証、本番確認が維持される。
- 改修のテスト・検証コマンドと実施範囲は次の Inception で決める。本書の保存で承認済み扱いにしない。

## 既存の共創計画の所在

今回検索した `docs/`、共有メモリ、Intent 文書の範囲では、Claude・Codex 共創専用の計画は特定できなかった。`docs/status-2026-10.md` の「AIDLC 移行時に決めること」に、以前の「Claude 設計 → Codex 実装」フローをどこまで残すかという論点がある。

これは専用の実装計画が存在する証拠ではない。GitHub、別リポジトリ、別の保存場所の計画は本調査では確認していない。既存計画が見つかったら本書は調査入力として統合し、重複した Intent や Bolt を作らない。
