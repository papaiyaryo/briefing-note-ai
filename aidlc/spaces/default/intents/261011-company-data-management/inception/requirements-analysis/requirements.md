# 企業メモ・選考状況管理の要件

## Intent Analysis

説明会メモを生成する単発の画面から、自分の企業メモと選考状況を継続して管理するアプリへ進める。PCとスマホで同じデータを開き、企業を選考状態ごとのボードで見渡し、対応中の社数を把握する。1企業に複数の手入力・OCR生成メモを保存し、修正した比較項目を使って企業を比較する。[Q1][Q2][Q3][Q6][Q12][Q13]

最初の1リリースは、この利用の流れをUI・API・保存・認証・検証まで含めて届ける。DBや認証サービスの名前、内部コンポーネント、実装順序、具体的な検証コマンドは後続の設計・計画で決める。文書の承認前にアプリ実装を始めない。[scope][memory:M1]

## Current Application and Change

現行はNext.js単一アプリで、画像→OCR→構造化→Web補足→Markdown編集・出力と面接前復習、ブラウザ保存メモの比較がある。独立した企業ID、選考状態、ユーザー所有権、サーバー側のメモ保存はない。比較保存の入口では構造化メモのprops接続が欠け、本文編集も比較用JSONを更新しない。これらは静的調査の所見であり、本番再現やテスト成功の証明ではない。[upstream:business-overview][upstream:architecture][upstream:code-structure]

今回、企業を保存・再表示できるようにし、企業IDに複数メモと選考状態を紐づける。保存の接続と比較用項目の編集は本機能を成立させる変更として扱う。その他の細かな既知不具合の一括修正は含めない。[Q5][Q6][Q12][Q13]

画面モックを見た人間の変更希望と変更確認Q1の回答aを受け、次の選考日を目立たせ、未応募とは別に検討中を設け、不採用・辞退は通常表示から隠す。終了した記録は削除せず必要時に再表示する。対応中は引き続き応募後の3状態だけを数える。この変更内容を要件として再確認する。[Q14]

## Functional Requirements

すべて今回のMust Have。固定IDは後の設計・Unit・検証へ引き継ぐ。各項目の操作・期待結果は受入確認に使い、具体的なテスト実行コマンドは後の計画で承認する。

### FR1 — 本人だけがPC・スマホから同じ保存データを使える

- **FR1.1** ログインした本人の企業・メモ・選考状態をサーバーに保存し、別端末から同じアカウントで読み出せる。他人への共有や共同編集は実装しない。[Q1]
- **FR1.2** 企業・メモの一覧、詳細、作成、編集、削除、比較に所有者確認を適用する。URLやIDを知っているだけではデータを取得・変更できない。[Q1][memory:M2]
- **FR1.3** ログアウト後や認証失効時に、保護された保存データを操作できない。再ログイン後に保存済みデータを再表示できる。一般向けの公開会員募集・共有権限管理は今回不要。[Q1]

受入条件:
- Given PCで本人が企業とメモを保存済み、When スマホから同じ本人としてログインして取得、Then 保存内容が一致する。
- Given 未認証、または別所有者の検証用アカウント、When 他の所有者のデータに直接アクセス、Then 内容が返らず更新も成立しない。試験は架空データで行う。

### FR2 — 企業名だけで企業を登録し、後から項目を管理できる

- **FR2.1** 企業名を必須にして企業を作成する。初期の選考状態は「未応募」。業界・志望度・自由記入の企業メモ・次の選考日・応募締切・公式サイトURLは空欄でもよい。[Q4][Q11]
- **FR2.2** 企業には名前と独立した安定IDを付ける。同じ企業のメモを増やしても企業レコードを増やさない。名称の一致だけで別企業を自動統合しない。[Q3][Q9]
- **FR2.3** 企業の項目と選考状態を後から編集する。名称変更後も所属メモを同じ企業に保つ。日付は日付として保持し、PC・スマホで日がずれない。[Q4][Q11]
- **FR2.4** 自由記入の企業メモは本人の記入として保持し、説明会の事実やWeb補足へ自動的に変換しない。[Q4][memory:M2]

受入条件:
- Given 保存企業0件、When 企業名だけ入力して登録、Then 新企業を未応募で表示し、任意項目は空欄のまま保存する。
- Given 空白だけの名前、無効な日付、危険なURL形式、When 保存、Then 対象欄のエラーを示し入力を保持する。空の任意項目はエラーにしない。
- Given 企業に2メモが所属、When 企業名を変更、Then メモ2件と企業IDを保持し、企業数は1のまま。

### FR3 — 選考状態ごとのボードと企業詳細を使える

- **FR3.1** 本人の企業の状態を「未応募／検討中／応募済／書類選考／面接／内定／辞退／不採用」の8種類とする。検討中は応募前に検討している状態で、未応募と独立する。初期状態は未応募のまま。通常のボードは未応募・検討中・応募済・書類選考・面接・内定の6状態を表示し、辞退・不採用は隠す。必要時に「終了した企業を表示」で2状態の企業も参照でき、カードから企業詳細と所属メモへ進める。非表示はデータ削除ではない。[Q2][Q9][Q14]
- **FR3.2** 8状態の選択欄で状態を明示変更し、保存成功後に該当列と社数へ反映する。辞退・不採用に変更した企業は通常表示から外れ、保存結果を示して終了企業の再表示へ進める。ドラッグ操作や表との切替は不要。非表示切替で保存状態を変更しない。[Q2][Q14]
- **FR3.3** 保存企業なし、表示条件により対象なし、読み込み中、取得失敗を区別する。保存企業0件なら登録へ進める。辞退・不採用だけが保存されている場合は、通常表示対象0件と終了企業の再表示方法を示し、全保存データ0件と扱わない。失敗時もデータ0件として確定表示しない。[Q1][Q2][Q14]
- **FR3.4** スマホでも登録・項目編集・状態変更・メモ閲覧編集・比較選択へ到達できる。通常6状態と終了企業の再表示操作で全8状態へアクセスでき、状態を色だけで表さない。[Q1][Q2][Q14]
- **FR3.5** 企業カードと企業詳細に「次の選考日」を独立した領域として表示し、状態やメモ件数などの補助情報より大きい太字と明示ラベルで目立たせる。日付未設定は「未設定」と文字表示し、推測の日付を補わない。応募締切とは別項目とし、色だけで意味を表さない。保存した日付は端末によってずれない。[Q11][Q14]

受入条件:
- Given 未応募と面接の企業が存在、When ボード表示、Then 各企業を対応する列に1回表示する。
- Given 各8状態の保存企業、When 通常のボード表示、Then 検討中を含む6状態を表示し辞退・不採用の列とカードを隠す。終了企業を表示すると2状態も参照でき、再び隠しても保存企業と所属メモは変わらない。
- Given 辞退・不採用の企業だけが保存、When 通常表示、Then 表示対象0件と終了企業の再表示方法を示し、保存企業0件とは表示しない。
- Given 検討中の保存企業、When 状態を変更保存して別端末で再取得、Then 同じ企業ID・所属メモ・確定状態を保つ。辞退・不採用への変更成功後は通常表示から外れても再表示で開ける。
- Given 保存した次の選考日と別の応募締切、When PCとスマホでカード・詳細を表示、Then 次の選考日を明示ラベル付きの強調領域で読め、締切と取り違えない。未設定なら日付を捏造せず未設定と表示する。
- Given 状態の変更保存が失敗、When 結果を表示、Then 成功扱いにせず変更前の確定状態と再試行方法を示す。
- Given PCとスマホの承認済み検証条件、When 主要操作を行う、Then どちらでも登録・編集・再表示・比較を完了できる。

### FR4 — 対応中社数と目標を表示し、15社以上だけ警告する

- **FR4.1** 対応中はエントリー後から最終結果または辞退までとする。「応募済・書類選考・面接」を数え、「未応募・検討中・内定・辞退・不採用」は数えない。途中の選考通過は対応終了にしない。[Q9][Q14]
- **FR4.2** 本人の企業ID単位で数え、メモ数や表示カード数で代用しない。ボードと集計は同じ保存状態を参照し、状態変更・企業削除の成功後に一致させる。終了企業を表示・非表示にしても集計を変えない。[Q3][Q9][Q14]
- **FR4.3** 対応中社数と目標5〜15社を表示する。15社以上のときだけ件数警告を表示する。5社未満への警告、15社超過による操作禁止、企業の自動追加・終了は行わない。[Q3][Q10]

受入条件:
- Given 対応中企業1社にメモ3件、When 集計、Then 対応中は1社。
- Given 検討中1企業にメモ3件、When 集計、Then 対応中には数えない。応募済へ変更保存すると1社増え、検討中へ変更保存すると1社減る。
- Given 応募後企業と終了企業が保存、When 終了企業の表示・非表示を切り替える、Then 対応中社数と15社警告は変わらず、保存状態を変更しない。
- Given 対応中0・4・5・14社の各データ、When 表示、Then 実件数と目標を表示し件数警告なし。
- Given 対応中15・16社の各データ、When 表示、Then 件数警告あり。16社目の登録・状態変更・メモ閲覧を禁止しない。
- Given 面接中の企業、When 最終内定・不採用・辞退へ変更して保存、Then 対応中から1社減る。途中の面接通過で選考継続する場合は減らない。

### FR5 — 元画像と見比べて確認したOCR生成メモを企業へ保存する

- **FR5.1** 既存の画像→OCR確認→構造化・Markdown生成を、選んだ企業のメモ保存へ接続する。生成中に元画像とテキストを見比べ、OCRテキストを修正できる。[Q5]
- **FR5.2** 原文にない企業事実を推測で補わず、読み取れない・不明な情報は要確認とする。紙メモ由来の各情報区分と、採用したWeb補足・出典URL・取得日を分離する。外部出力は構造を検証してから扱う。[Q5][memory:M2]
- **FR5.3** 生成したメモの編集本文、構造化項目、原文確認に使うOCRテキストとイベント情報、採用Web補足の出典情報をテキスト／構造化データとして保存する。元画像のバイナリをアプリのDB・画像ストレージ・localStorageへ永続保存しない。[Q5]
- **FR5.4** 原画像は見比べ中の一時表示に用い、不要後に一時参照を解放する。外部OCRサービス側の保持条件はアプリ側の画像非保存と区別し、設計で確認する。[Q5][memory:M2]
- **FR5.5** 生成結果の企業名だけで別企業を作ったり選択企業の名称を書き換えたりしない。生成失敗・不正出力は成功メモとして保存せず、確認・修正の導線を保つ。[Q5][Q12]

受入条件:
- Given 選択企業と架空の画像／OCR入力、When OCR訂正・生成・内容確認後に保存、Then 同じ企業のメモとして再表示でき、元画像の永続データは存在しない。
- Given 原文で確認できない数字や空の項目、When 生成結果を扱う、Then 根拠なしの事実を確定情報にせず要確認または未記載として区別する。
- Given Web補足付きのメモ、When 保存・再表示、Then 紙メモ由来の情報と別区分で、採用補足のURL・取得日を保持する。
- dummy出力は検証用／デモ由来として判別でき、実企業の確定事実として無表示で扱わない。CIは実OCR・LLMの成功を保証する試験にしない。

### FR6 — 手入力と生成メモを企業ごとに複数保存し、開いて編集する

- **FR6.1** 画像なしの手入力メモを新規作成できる。本人の自由記入をLLMで自動構造化したり企業事実へ昇格したりしない。[Q12][memory:M2]
- **FR6.2** 各メモに安定IDを持たせ、1企業に複数メモを保存する。企業詳細から選んだメモを開き、本文・関連項目の変更を保存して再表示できる。[Q5][Q12]
- **FR6.3** 未保存の変更と保存済みを区別する。保存失敗時は編集内容を保持して再試行でき、成功通知を出さない。画面移動による未保存内容の破棄は確認する。[Q5][Q12]
- **FR6.4** 企業・メモの削除では、対象と影響する所属メモを明示して確認する。キャンセル時は変更しない。企業の削除は所属メモ・比較候補・社数に一貫して反映する。既存localStorageの旧データをこの操作で削除しない。[Q1][Q5][Q7][Q12][assumption:A2]

受入条件:
- Given 企業に生成メモ1件、When 手入力メモを追加し別端末で取得、Then 同じ企業に2件あり、企業数は増えない。
- Given メモ本文を変更して保存、When 再表示、Then 変更本文が一致する。構造化項目は本文変更だけで自動的に書き換わらない。
- Given 保存の通信失敗、When 結果表示、Then 入力を保持し、未保存であることを表示する。
- Given 削除確認、When キャンセル、Then 企業・メモ・件数に変更なし。確定削除では対象の所属関係を残さない。

### FR7 — 比較用の構造化項目を編集し、本文と区別する

- **FR7.1** 保存メモの事実・事業・強みなど、既存比較が使う構造化項目を編集できる。修正を保存すると比較が参照する同じメモの項目へ反映する。[Q13]
- **FR7.2** 編集本文と構造化項目は別の正本として扱い、それぞれの用途を画面で示す。本文からJSONを自動再生成する機能は今回不要。入力がない比較項目を架空データで埋めない。[Q13][memory:M2]
- **FR7.3** 構造化項目も事実・印象・HR強調・質問・ES材料・Web補足の境界を維持する。Web補足を原文由来の事実へ混ぜず、出典を保持する。[Q5][Q13][memory:M2]

受入条件:
- Given 保存済み構造化メモ、When 強みの項目を修正して保存し比較を再取得、Then 修正後の値を使用する。
- Given 本文だけを修正、When 比較、Then 構造化項目は勝手に書き換わらず、比較の参照元が分かる。
- Given 不正な構造化データ、When 保存、Then 拒否して前の有効データと編集内容を保持する。

### FR8 — サーバー保存したメモから企業比較を使える

- **FR8.1** 本人の保存企業と、その比較に使う構造化メモを選んで既存の比較観点を表示する。企業ごとに参照メモを明示する。[Q6][Q13][assumption:A3]
- **FR8.2** 最新の保存済み構造化項目を使い、欠けた情報は未記載／要確認として扱う。手入力の自由本文を自動で事実として比較しない。[Q6][Q13]
- **FR8.3** 別端末でも本人のサーバー保存データから比較できる。比較表示と既存の比較Markdown出力を同じ参照データに基づかせる。[Q1][Q6][upstream:business-overview]
- **FR8.4** 旧localStorageの比較データは移行・自動削除しない。新しい比較と旧データ参照の区別を設計で明示する。[Q7]

受入条件:
- Given 本人の企業2社と構造化メモ、When 参照するメモを選択して比較、Then 各社の選択メモの保存済み項目と出典を使用する。
- Given 同一企業のメモが複数、When 比較対象を選択、Then メモを別企業として重複カウントせず、どのメモを使うかが分かる。
- Given 比較対象なし／構造化項目なし／取得失敗、When 表示、Then それぞれの状態を区別し、架空の比較結果や成功出力を作らない。

### FR9 — 既存の出力・復習導線を保ち、今回の変更範囲を明示する

- **FR9.1** 既存の編集Markdown、比較Markdown、面接前復習Markdownのダウンロード導線を維持する。メモの手編集とWeb出典の区分を出力でも保持する。[Q7][upstream:business-overview]
- **FR9.2** 既存の面接前復習機能は利用可能な導線を保つが、新しいサーバー保存データとの復習連携・復習結果の永続保存は今回行わない。[Q6]

受入条件:
- Given 生成・編集メモまたは比較結果、When 既存のダウンロード操作、Then 表示／編集した対応データを.mdとして出力できる。
- Given 既存の生成フロー、When 面接前復習の導線を使用、Then 今回の企業管理変更で導線を消さない。既知の中断処理不具合の修正承認をこの条件に含めない。

## Non-Functional Requirements

### NFR1 — 所有者分離と秘密情報

本人の認証を全保護操作で確認し、他所有者ID・不正ID・未認証の直接APIアクセスから企業／メモ／比較内容を取得・変更できない。外部サービスの秘密情報はサーバー側で扱い、実メモ・OCR本文・画像・キーを不要にログや開発記録へ出さない。[Q1][memory:M2]

検証: 架空の本人・別所有者・未認証のケースで一覧／詳細／更新／削除／比較を確認し、返却データと変更の有無を判定する。

### NFR2 — 保存と障害時の整合性

保存成功と表示したデータは再取得できる。企業とメモの所属関係、選考状態と社数を一貫させる。保存・削除の部分成功や二重送信で重複企業／メモを黙って作らず、失敗時は元の有効データと入力を保持する。読み込み失敗は0件表示と区別する。[Q1][Q5][Q12]

検証: 通信失敗、ストア失敗、二重送信、所属メモのある企業削除を架空データで確認する。新しい保存APIのタイムアウト／再試行の具体値は設計で定め、無期限待ちや無制限再試行は認めない。

### NFR3 — 複数端末の変更

PCで保存した内容をスマホで再取得すると一致する。別端末の古い内容による上書きを検出し、黙って保存済み変更を失わない。常時リアルタイム配信・オフライン編集同期は今回対象外。[Q1]

検証: 2つの検証クライアントで同じ記録を読み、先行保存後に古い内容を保存した場合、競合を通知し編集入力を保持する。

### NFR4 — 原文への忠実性と情報区分

確認用のOCRテキストと構造化データ、手編集本文、本人の自由記入、Web出典を混同しない。原文にない情報を確定事実として追加せず、不明情報を要確認とする。元画像のアプリ永続保存なしは検証可能な保存契約に含める。[Q5][Q13][memory:M2]

検証: 原文にない値・読取不能箇所・Web情報・本文だけの修正・構造化項目の修正を含む架空fixtureで、区分と比較への反映を確認する。実OCRの全入力での正解率を100%と約束する要件ではない。

### NFR5 — PC・スマホと安全な表示

日本語UIの主要操作をPC・スマホで行える。状態や警告を色だけに依存させず、PCではキーボードでも操作できる。Markdownや企業名にHTML・スクリプト風の文字列があっても実行しない。URLは安全な形式だけをリンクにする。[Q1][Q2][memory:M2]

検証: 後の画面設計・検証計画で承認するPC／スマホ表示条件、キーボード操作、架空の長文・日本語・危険な文字列で確認する。

### NFR6 — 検証とリリース品質

TDDのRed→Green→Refactorと既存の検査を維持し、Classicのline coverage 80%下限を満たす計測・対象・CI設定を計画する。現在は測定設定がなく達成未確認。CIはdummy providersと架空データを使い、実APIの秘密情報に依存しない。[memory:M1][upstream:team-practices]

受入確認はVitestと手動の利用導線確認を基本にする。npm run lint、npm run typecheck、npm test、npm run buildと受入証拠を揃え、Docker変更時はDockerも確認する。本番は実merge SHAのデプロイ、ページ、health、承認済み利用導線を確認する。[memory:M1]

### NFR7 — 費用と規模

無料枠を第一条件として保存・認証を設計し、収まらない場合は課金や要件縮小を勝手に決めず相談する。無料枠の条件・上限・休止や失効時の影響は設計で調べる。対応中15社は費用上限・企業登録上限とは区別し、16社以上でも警告以外の制限を加えない。[Q8][Q10]
