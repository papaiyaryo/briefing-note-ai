## Persona and Priority

全ストーリーの主体は`personas.md`のP1（本人の説明会・選考準備を管理する求職者）。すべて **Must Have**。他所有者・未認証はアクセス境界の試験役であり、新たな共同利用ペルソナではない。

## Common Acceptance Rules

- 各保存操作はサーバー側で本人と対象の所有権を確認する。未認証・別所有者・不正IDの直接API要求を拒否し、データを漏らさず変更しない（US1.1／US1.2）。秘密情報はサーバー側、実画像・本文・OCR・キーを試験や不要なログへ入れない。
- 読込中・空・失敗・保存済み・未保存・保存結果不明を混同しない。明示拒否なら前の有効データと入力を保つ。応答途絶では書込成功の可能性があるためロールバックを断定せず再取得で確認し、同じ操作の再試行で重複作成しない。
- 企業名・本文・比較・Markdownは危険な文字列を実行しない。URLは安全な形式だけリンクにし、状態と警告は文字でも表す。主要操作は承認予定のPC／スマホ条件とPCキーボードで確認する。
- 編集本文と構造化項目は別正本。説明会事実・本人の印象・HR強調・質問・ES材料・Web補足を分離し、不明は要確認。手入力を自動的に事実化しない。
- 架空fixtureとdummy providerで受入を確認する。実OCR／LLM全入力の正解率や未調査の無料枠・性能を保証しない。

## Stories

### US1.1 — 本人としてログインし、安全に利用を終える

本人（P1）として、本人としてログイン・ログアウトしたい。それにより、自分の保存データだけを安心して使える。

- Priority: **Must Have**
- 要件: FR1, FR1.2, FR1.3, NFR1
- 関係: 独立した入口として検証できる。 テストでは架空の初期状態を用意し、前ストーリーの実行を必須にしない。

#### Acceptance Criteria

- **AC1.1.1** Given 本人の有効な認証手段がある、When ログインして企業一覧を取得する、Then 本人の保存データを表示し、他所有者のデータを含めない。
- **AC1.1.2** Given 未認証または認証失効、When 一覧・詳細・作成・更新・削除・比較を直接要求する、Then 保護された内容を返さず変更を成立させない。
- **AC1.1.3** Given ログイン済み、When ログアウトする、Then 保護画面のデータを操作できず、残った画面や取得応答から再表示しない。
- **AC1.1.4** Given 認証に失敗、When 結果を表示する、Then 保存データ0件と混同せず再試行方法を示す。再ログイン後は保存済みデータを取得できる。

### US1.2 — 別端末で自分のデータを再取得する

本人（P1）として、PCとスマホで同じ企業とメモを開きたい。それにより、端末を変えても準備を続けられる。

- Priority: **Must Have**
- 要件: FR1, FR1.1, FR1.2, NFR1, NFR3
- 関係: US1.1の利用データ／操作を使う。 テストでは架空の初期状態を用意し、前ストーリーの実行を必須にしない。

#### Acceptance Criteria

- **AC1.2.1** Given PCで企業・メモ・選考状態を保存済み、When 同じ本人がスマホで再取得する、Then ID・本文・構造化項目・状態・日付が一致する。
- **AC1.2.2** Given 別所有者の架空IDまたは不正ID、When 一覧・詳細・作成時の親参照・更新・削除・比較のAPIを直接要求する、Then 相手の内容を取得できず相手のデータは変化しない。
- **AC1.2.3** Given 取得の通信失敗、When 別端末で開く、Then 空の一覧と確定せず、失敗を示し再取得できる。
- **AC1.2.4** Given 別端末で変更済み、When 明示的に再取得する、Then 最新の保存内容を表示する。常時配信・オフライン同期を前提にしない。

### US2.1 — 企業名だけで登録する

- Priority: **Must Have**

- 関係: US1.1の利用データ／操作を使う。 テストでは架空の初期状態を用意し、前ストーリーの実行を必須にしない。

#### Acceptance Criteria

- **AC2.1.1** Given 保存企業0件、When 企業名だけで登録する、Then 安定IDを持つ企業が未応募で1件保存され、任意項目は空欄のままである。
- **AC2.1.2** Given 名前が空または空白だけ、When 保存する、Then 名前欄のエラーを示し入力を保持し、企業を追加しない。
- **AC2.1.3** Given 同名の保存企業がある、When 新しい企業を明示登録する、Then 名称一致だけで自動統合しない。
- **AC2.1.4** Given 1回の登録意図、When 二重送信または結果不明後の確認・再試行を行う、Then 同じ操作による重複企業を黙って作らず、確定結果と入力を保つ。

### US3.1 — 選考ボードから企業とメモを開く

本人（P1）として、企業を状態別に見渡して詳細へ進みたい。それにより、対応先と準備内容を見失わずに選べる。

- Priority: **Must Have**
- 要件: FR3, FR3.1, FR3.3, FR3.4, FR3.5, NFR5
- 関係: US2.1の利用データ／操作を使う。 テストでは架空の初期状態を用意し、前ストーリーの実行を必須にしない。

#### Acceptance Criteria

- **AC3.1.1** Given 本人の企業が保存8状態にある、When 通常のボードを開く、Then 未応募・検討中・応募済・書類選考・面接・内定の6状態で該当企業を各1回表示し、辞退・不採用の列とカードを隠す。検討中は応募前の検討状態として未応募と別に扱う。
- **AC3.1.2** Given 企業カード、When 開く、Then 同じ企業の詳細と所属メモ一覧に到達する。
- **AC3.1.3** Given 取得前・取得成功0件・取得失敗、When 画面を表示する、Then 読込中・空・失敗を区別し、空は企業登録、失敗は再取得へ進める。

- **AC3.1.5** Given 状態や警告の表示、When 色を識別せず読む、Then 文字でも意味を判断できる。
- **AC3.1.6** Given 辞退・不採用の保存企業と所属メモ、When 「終了した企業を表示」を有効にする、Then 2状態の列とカードも各1回表示し、詳細と所属メモへ進める。再び隠しても企業・所属メモ・保存状態を変更しない。PCとスマホでこの操作に到達できる。

- **AC3.1.8** Given 次の選考日と別の応募締切を保存した企業、および選考日未設定の企業、When PCとスマホでカード・詳細を表示する、Then 次の選考日を明示ラベル付きの独立領域に、状態やメモ件数より大きい太字で示す。保存した暦日を変えず、締切と区別し、未設定は「未設定」と文字で示し日付を補わない。

### US3.2 — 選考状態を変更する

本人（P1）として、選択欄で状態を変更したい。それにより、選考の進み具合を保存して追える。

- Priority: **Must Have**
- 要件: FR3, FR3.2, FR4.1, FR4.2, NFR2
- 関係: US3.1の利用データ／操作を使う。 テストでは架空の初期状態を用意し、前ストーリーの実行を必須にしない。

#### Acceptance Criteria

- **AC3.2.1** Given 保存企業、When 未応募・検討中・応募済・書類選考・面接・内定・辞退・不採用の8状態の選択欄から変更し保存が確定する、Then 同じ企業IDと所属メモを保ち、表示条件に応じた対応列と集計へ同じ確定状態を反映する。別端末で再取得した状態も一致する。
- **AC3.2.2** Given 状態保存が明示拒否、When 結果を表示する、Then 成功にせず変更前の確定状態と再試行方法を示す。
- **AC3.2.3** Given 状態保存の応答が途絶、When 結果を表示する、Then 未確定と示して再取得で確認でき、成功またはロールバックを推測で断定しない。
- **AC3.2.4** Given 面接中の企業、When 途中通過後も選考を継続する、Then 対応中に残る。最終内定・辞退・不採用の保存確定後は対応中から外れる。
- **AC3.2.5** Given 通常表示中の企業、When 辞退または不採用への変更保存が確定する、Then カードは通常表示から外れ、保存結果と終了企業の再表示方法を示す。再表示から同じ企業の詳細とメモを開け、非表示操作だけでは保存状態を変更しない。
- **AC3.2.6** Given 検討中の企業、When 応募済へ変更保存してから検討中へ戻し保存する、Then 検討中と未応募を混同せず、各確定状態をボードと別端末の再取得へ反映する。企業や所属メモを複製しない。

- **AC6.2.4** Given 未保存変更、When アプリ内画面移動で破棄しようとする、Then 確認し、キャンセルは編集を続ける。対応ブラウザの離脱確認の扱いは画面設計で具体化する。
- **AC6.2.5** Given 本文にHTML・スクリプト風文字列、When 編集・プレビュー・再表示する、Then 実行せず安全に表示する。

### US6.3 — 端末間の古い上書きを防ぐ

本人（P1）として、競合を知って編集内容を保ちたい。それにより、別端末で保存した修正を黙って失わずに済む。

- Priority: **Must Have**
- 要件: NFR3, NFR2, FR2.3, FR3.2, FR6.2, FR7.1
- 関係: US1.2, US6.2の利用データ／操作を使う。 テストでは架空の初期状態を用意し、前ストーリーの実行を必須にしない。

#### Acceptance Criteria

- **AC6.3.1** Given 2クライアントが同じ企業またはメモの旧版を取得、When 先行保存後に後行クライアントが古い版を保存する、Then 競合を検出して後行の古い更新を黙って確定しない。
- **AC6.3.2** Given 競合検出、When 結果を表示する、Then 後行の編集入力を保持し、最新内容を確認して再編集できる。
- **AC6.3.3** Given 最新版を再取得して変更を確認、When 明示的に再保存する、Then 成功確定後の内容が両端末の再取得で一致する。
- **AC6.3.4** Given 競合対象が企業項目・選考状態・本文・構造化項目の各ケース、When 古い変更を送る、Then 同じ無言上書き防止を適用する。自動マージを期待しない。

### US6.4 — 確認してメモを削除する

本人（P1）として、選んだメモを確認して削除したい。それにより、不要な記録だけを整理できる。

- Priority: **Must Have**
- 要件: FR6, FR6.4, FR8.1, NFR2
- 関係: US6.2の利用データ／操作を使う。 テストでは架空の初期状態を用意し、前ストーリーの実行を必須にしない。

#### Acceptance Criteria

- **AC6.4.1** Given 所属メモ、When 削除確認を開く、Then 対象企業と対象メモを明示し、キャンセルではデータを変えない。
- **AC6.4.2** Given 確認後の削除が確定、When 一覧を再取得する、Then 対象メモだけを除き、企業・他メモ・企業数を保つ。
- **AC6.4.3** Given 対象を比較参照中、When 削除が確定する、Then 古い参照を無効化して再選択を促し、削除前の結果を最新比較として使わない。
- **AC6.4.4** Given 拒否または結果不明、When 結果を示す、Then 成功と断定せず再取得で確認でき、旧localStorageのデータを変更しない。
- **AC6.4.5** Given 削除確認を開いた後に別端末で対象メモが編集された、When 古い確認で削除を要求する、Then 削除を止め、最新内容と変更を取得して再確認を求める。再取得に失敗したまま削除せず、既に削除済みならその状態を示して他のメモを削除しない。

### US6.5 — 所属メモも確認して企業を削除する

本人（P1）として、削除の影響を見て企業を整理したい。それにより、所属メモを含む対象を理解して管理できる。

- Priority: **Must Have**
- 要件: FR6, FR6.4, FR4.2, FR8.4, NFR2
- 関係: US3.1, US6.4の利用データ／操作を使う。 テストでは架空の初期状態を用意し、前ストーリーの実行を必須にしない。

#### Acceptance Criteria

- **AC6.5.1** Given メモ2件を持つ企業、When 企業削除の確認を開く、Then 対象企業と所属メモ2件が削除対象であると示し、キャンセルで何も変更しない。
- **AC6.5.2** Given 明示確認後に削除が確定、When ボード・メモ一覧・比較候補・集計を取得する、Then 企業と所属メモを一貫して除き孤立メモを残さない。
- **AC6.5.3** Given 所属削除処理の明示失敗、When 保存状態を確認する、Then 部分削除を成功扱いせず元の有効な所属関係を維持する。通信結果不明では再取得で確定結果を確認する。
- **AC6.5.4** Given 比較で削除企業を選択中、When 再取得する、Then 対象参照を無効化し最新の比較として出力しない。
- **AC6.5.5** Given 旧localStorageデータがある、When サーバー企業を削除する、Then 旧データを自動削除・移行しない。
- **AC6.5.6** Given 所属メモ2件の企業削除を確認した後、別端末で企業・所属メモの編集または3件目の追加があった、When 古い確認で削除を要求する、Then 削除を止め、最新の対象・件数・変更を取得して再確認を求める。最新取得の失敗中は削除できず、既に削除済みならその状態を示す。新しい明示確認なしで変更後のデータを削除しない。

### US7.1 — 比較用項目を本文と別に編集する

本人（P1）として、構造化された比較項目を修正したい。それにより、修正した情報で企業を比べられる。

- Priority: **Must Have**
- 要件: FR7, FR7.1, FR7.2, FR7.3, NFR4
- 関係: US6.2の利用データ／操作を使う。 テストでは架空の初期状態を用意し、前ストーリーの実行を必須にしない。

#### Acceptance Criteria

- **AC7.1.1** Given 保存された構造化メモ、When 事実・事業・強みなど既存比較の項目を修正保存し比較を再取得する、Then 同じメモの修正後の値を用いる。
- **AC7.1.2** Given 本文と構造化項目の編集画面、When 編集する、Then 用途と参照元を示し、本文変更だけでJSONを再生成せず、項目変更だけで本文を書き換えない。
- **AC7.1.3** Given 未記載項目または不正な構造入力、When 保存する、Then 未記載を架空値で埋めず、不正入力は拒否して前の有効データと編集入力を保つ。
- **AC7.1.4** Given 事実・印象・HR強調・質問・ES材料・採用Web補足、When 項目を編集保存する、Then 区分を保ちWeb出典URL・取得日を失わない。

### US8.1 — 企業ごとにメモを選んで比較する

本人（P1）として、各企業の比較に使うメモを選びたい。それにより、参照元を確かめて保存情報を比べられる。

- Priority: **Must Have**
- 要件: FR8, FR8.1, FR8.2, FR8.3, FR8.4, NFR1, NFR4
- 関係: US1.2, US7.1の利用データ／操作を使う。 テストでは架空の初期状態を用意し、前ストーリーの実行を必須にしない。

#### Acceptance Criteria

- **AC8.1.1** Given 本人の企業2社と構造化メモ、When 各社1メモを選んで比較する、Then 企業と参照メモを明示し最新の保存済み項目・出典で既存比較観点を表示する。
- **AC8.1.2** Given 同じ企業に複数メモ、When 対象を選択・切替する、Then 1社として扱い、選択した1メモへ参照を切り替え、自動統合しない。
- **AC8.1.3** Given 本文のみのメモまたは欠けた比較項目、When 比較する、Then 本文を自動事実化せず未記載／要確認と示す。構造化項目なしは選択できる有効な構造化メモと区別する。
- **AC8.1.4** Given 対象なし・取得失敗・不正構造・未認証・別所有者ID、When 比較を要求する、Then 各状態を区別し、架空結果や成功出力を作らず他人の内容を返さない。
- **AC8.1.5** Given 旧localStorage比較データ、When 新しい比較を開く、Then サーバー保存データの参照と旧データ参照を区別し、自動移行・自動削除をしない。

### US9.1 — 対応するMarkdownをダウンロードする

本人（P1）として、メモ・比較・既存復習を.mdで出力したい。それにより、手元の準備資料として使える。

### US9.2 — 既存の面接前復習へ進む

## INVEST and Delivery Boundaries

各ストーリーは1つの利用者の目的と観察可能な結果を持ち、成功・拒否・結果不明・境界を受入条件で区別する。初期データfixtureを用いて独立検証できるが、認証や保存などの機能依存は明記する。UIだけ／APIだけをリリースする分割はしない。契約・画面・データを設計した後に工数とUnit粒度を評価し、大きすぎる場合は同じ承認範囲のままDelivery Planningで依存Unitへ分ける。現時点で実装時間の見積りを確定したとは扱わない。

## Downstream Decisions and Open Questions

- **R-01（要件レビューから継承）**: 企業項目の志望度・企業メモと、選択メモが持つ比較用志望度・理由の正本関係は未決定。US2.2／US7.1／US8.1の共通設計として、編集後・参照メモ切替後の値をDomain Designで確定し、画面と受入例へ反映する。勝手な同期・複製規則をここで追加しない。旧localStorageの参照区別も設計する。
- **R-02（要件レビューから継承）**: 架空の代表企業数・メモ数・本文量、操作ごとの応答目標と測定条件は未決定。Domain Design／Delivery Planningで無料枠調査と合わせて定める。15社警告は保存上限でも性能試験上限でもない。
- 認証方式・本人アカウント作成・DB候補・所有権・競合検出・入力上限・タイムアウト・有限再試行・削除の一貫性・外部OCR保持条件は設計で定める。アプリの画像非保存と外部サービスの保持は区別する。
- PC／スマホ表示条件、危険入力・長文fixture、ブラウザ離脱確認、旧比較参照、比較項目の具体編集UIはRefined MockupsとDomain Designで定める。
- **NFR6**はDelivery Planning／Build and TestでTDD、80% line coverage計測、lint／typecheck／test／build、必要時Docker、手動フロー、CIと実merge SHAの本番確認へ対応付ける。具体コマンド承認をこの文書で代行しない。
- **NFR7**の無料枠・容量・停止時の影響と性能条件はDomain Designに引き継ぐ。無料と未確認のまま実装計画を承認しない。

## Out of Scope
