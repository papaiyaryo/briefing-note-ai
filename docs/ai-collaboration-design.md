# AI共創と記録の軽量化 設計案

- 作成: 2026-11-06（Claude Code）
- 状態: **案（未承認）**。Bolt 2 完了後、次のアプリ Bolt の前に方針を決めるための文書。現在の Intent・承認・memory を変更しない。
- 前提資料: `aidlc/spaces/default/knowledge/documents/2026-10-25-token-efficiency-and-claude-codex-collaboration.md`（Codex の調査と共創案）。本書はそれを実測で補い、実施手順まで落とす。

## 1. 何がトークンを使っているか（実測）

対象: Codex のローカルセッション記録 14 件（2026-10-30〜11-06、Bolt 2 の Build and Test 期）。メタデータのみ集計し、内容は転記していない。

| 指標 | 値 |
|---|---:|
| 入力トークン合計 | 37.1M（キャッシュ 80〜98%） |
| モデル呼び出し回数 | 432 |
| 1 呼び出しあたりの平均文脈 | 約 86k |
| 1 呼び出しで終わったセッションの文脈（固定分） | 約 26k |
| ツール出力のうち待機・ポーリング | 35%（138 回） |

**仕組み:** 入力 = 呼び出し回数 × その時点の文脈。一度読んだファイルは、その後のすべての呼び出しで送り直される。したがって「大きなファイルを 1 回読む」ことと「呼び出し回数が多い」ことが掛け算で効く。

**文脈の中身（推定）:** 公式フレームワークの指示をセッションごとに読み込んでいる。
`SKILL.md` 88KB、`stage-protocol.md` 104KB、`stage-protocol-construction.md` 70KB、`stage-protocol-reviewer.md` 46KB で計約 300KB（英語で約 7〜8 万トークン）。平均文脈 86k とほぼ一致するので、**文脈の大部分は公式の指示文**と考えられる。

**目的に対して読みすぎの候補:** `knowledge/` 配下の参考資料（verification、brownfield、rules-reading、quality-agent 向けの各ガイド）を、セッションごとに繰り返し読んでいる（読み込み出力の延べ合計は約 1.3MB。1 コマンドで複数のファイルを読むと重複して数えるため、概算）。stage がそれらを名指ししていたかは未検証。

**記録（Intent 261011）:** 392 ファイル、4.7MB（ほかに、モデルが読まない `.aidlc-engine/` が 127MB）。

| 区分 | ファイル数 | サイズ | 備考 |
|---|---:|---:|---|
| 監査ログ | 1 | 1.2MB | エンジンが追記する。通常は読む必要がない |
| バックアップ複製（`*before*`、`archive/`、`initial-revision`） | 49 | 0.8MB | Git 履歴と重複する |
| JSON（traceability、inventory など） | 45 | 0.9MB | 一覧をそのまま記録に入れている |
| レビュー | 51 | 0.26MB | 公式プロトコルの成果物 |
| 画像・HTML（モックアップ） | 10 | 0.45MB | 読む必要はない |

**集計範囲外:** 10/24 以前に大量に消費したセッション（入力 1.5B トークン）、Claude 側の消費、hook が注入する文脈（約 1.8M 字。中身は未分類）。

**結論:** ボトルネックは「記録が長いこと」そのものではなく、**(1) 毎回送り直される大きな文脈、(2) 必要のない資料の読み込み、(3) 待機のために何度もモデルを呼ぶこと**。過去の記録は読まなければコストにならない。

## 2. 原則

1. **呼び出し回数を減らす**: いちばん効く。待機・確認のための呼び出しをなくす。
2. **文脈に入れるものを減らす**: 読むなら要約や該当箇所だけ読む。大きな読み込みは別の文脈（サブエージェント）で行い、結論だけを受け取る。
3. **記録は「次に読まれる」前提で短く書く**: 要約を正本にし、詳細は Git 履歴と生成スクリプトに任せる。
4. **守るもの**: 公式 runtime は改造しない。承認ゲート・TDD・公式レビュー・検証・本番確認は削らない。

## 3. 共創の運用

### 役割（案）

工程ごとの担当は「既定」であって固定ではない。片方が数日進めている間、もう片方の利用枠が使われないまま期限を迎えないよう、**利用枠の残っている側が区切りで進行を引き継ぎ、進行していない側は「並走レーン」の仕事をする**。

| 工程 | 既定の進行担当 | 交代の目安 |
|---|---|---|
| Inception（要件・設計・レビュー） | Claude | Claude の利用枠が尽きたら、stage の区切りで Codex へ |
| Construction（Code Generation、Build and Test） | Codex | Codex の利用枠が尽きたら、Unit の区切りで Claude へ |
| リリース・本番確認 | 人間 | — |

既定の理由: Claude はサブエージェントで大きな読み込みを本文から切り離せるので、読む量の多い工程に向く。実装は従来どおり Codex を主にする。

### 並走レーン（進行していない側の仕事）

共有の状態・承認・承認済み成果物に触れず、別の worktree か自分の文書だけで完結する仕事。優先度の高い順に並べる。

1. **進行中の差分の読み取りレビュー**: 進行担当がコミットした差分を読み、指摘を自分の文書に書く。採用するかは進行担当と人間が決める。公式レビューの代わりにはしない。
2. **テスト・検証の下調べ**: 不安定なテストの原因調査、手動受入の手順書の下書き、失敗ログの要約。
3. **次の Bolt の下調べ**: 現行画面の調査、本番確認のフィードバックの整理、要件のたたき台。いずれも `knowledge/documents/` の調査文書にとどめる。公式の Inception は今の Bolt の本番確認後に始める（project.md の規則）。
4. **tooling と運用**: 本書の tooling PR、hook の計測、upstream への要望、記録の要約。アプリコードには触れない。

並走レーンの仕事は、人間がその都度頼む。進行していない側が、自分の判断で仕事を始めない。

### 司令塔方式（試行案、2026-11-07 追記）

Claude を唯一の進行担当（司令塔）にし、Codex を `codex exec`（対話なしで 1 つの依頼を実行し、結果を返すモード）で実行役として呼ぶ。

| 役割 | 担当すること | 触らないもの |
|---|---|---|
| Claude（司令塔） | AI-DLC の進行（`next` / `report`、人間への承認依頼）、タスクの切り出し、Codex の差分のレビュー、テストの再実行と TDD 証拠の記録 | — |
| Codex（実行役） | 1 タスク = 1 回の `codex exec`。専用の worktree で実装とテストを行い、結果を要約して返す | AI-DLC のコマンド・状態・記録、承認、push |

呼び出し方の案:

```text
codex exec -C <Codex 用 worktree> -s workspace-write --ephemeral \
  -c features.hooks=false -o <結果ファイル> "<タスク指示>"
```

**最大の危険**: AI-DLC の hook が動く場所で `codex exec` を使うと、Claude の指示が「人間の発言」として監査記録に残るおそれがある（人間の入力の偽装にあたる。project.md の禁止事項）。後から見分けられないので、**一つの設定に頼らず、次の 4 層で起こり得ない形にする**。

1. **Codex の作業場所に AI-DLC のファイルを置かない（主対策）**: Codex 用 worktree は sparse checkout で作り、`.codex/`、`.agents/`、`.claude/`、`aidlc/`、`AGENTS.md` を含めない。読み込む hook も、書き込む先の記録も存在しない。AGENTS.md のうち実装に必要な規則（lint、TDD、秘密情報）は、タスク指示に書いて渡す。
2. **信頼されていない場所で動かす**: Codex の hook の信頼は、絶対パス `D:\briefing-note-ai\.codex\hooks.json` にだけ記録されている（2026-11-07 確認）。Codex 用 worktree は別のパスに置くので、仮に hook ファイルがあっても動かない。`--dangerously-bypass-hook-trust` は絶対に使わない。
3. **hook の機能自体を切る**: `-c features.hooks=false`（予備の層。これだけには頼らない）。
4. **毎回、事後に確かめる**: Claude は `codex exec` の前後で、本体の監査ログと `aidlc/.aidlc-sessions/` のハッシュを比べる。変化があれば作業を止めて人間に報告する。

Codex を `D:\briefing-note-ai` 本体（AI-DLC の記録があるチェックアウト）で `codex exec` として動かすことはしない。差分は、Claude が Codex 用 worktree から取り出し、レビューしてから進行用のチェックアウトに適用する。
- **指示文に `$aidlc` を書かない**: スキル全文（88KB）を読み込ませないため。Codex は毎回、小さな文脈から始まる。
- **指示は具体的に書く**: 対象ファイル、通すべきテスト、守る規則（TDD、既存の lint 設定）、変更してはいけない範囲。結果は `--output-schema` で形を決めて受け取る。
- **Claude が必ず確かめる**: 差分を読み、テストを自分で再実行してから記録に残す。Codex の報告をそのまま証拠にしない。

期待できること:

- 両方の利用枠を同時に使える（Claude が進行し、Codex が実装する）。
- Codex は AI-DLC の指示文（約 7〜8 万トークン）を毎回読まずに済む。
- Claude の文脈に入るのは、Codex の読み込み全体ではなく結果だけ。

懸念:

- Claude は進行担当として公式の指示文を抱えるので、Claude の利用枠の消費が増える。stage ごとに開き直して抑える。
- Codex に実装を任せる運用は、現在の team.md / AGENTS.md（Codex harness が主）と異なる。試行の結果を見て、次の Inception で人間の承認を得て規則にする。
- Construction の Unit は直列という規則は変えない。並行させるのは、互いに独立したタスクだけにする。

試行 1 の結果（2026-11-07、Codex CLI 0.166.0）: `D:/bnai-codex-task`（sparse checkout で AI-DLC のファイルを除外）で、`codex exec -s read-only --ephemeral -c features.hooks=false` に package.json についての質問を 1 つ出した。19 秒、**4,847 トークン**で正しく答えた（対話セッションの 1 呼び出し平均は約 86k）。本体の AI-DLC 記録 888 ファイルのハッシュは前後で一致し、エンジンの作業領域も含めて更新されたファイルは 0 件だった。worktree の変更も 0 件。Git Bash では sparse checkout のパターン（`/.codex/` など）が Windows のパスに変換されてしまうため、`MSYS_NO_PATHCONV=1` を付け、worktree のパスは `D:/…` の形で書く。

試行の手順:

1. 上の 1〜3 の層を備えた Codex 用 worktree（別パス、sparse checkout）を作る。その中で `codex exec` に読み取りだけの小さな依頼を出す。実行の前後で、本体の監査ログと `.aidlc-sessions/` が変わらないこと、worktree に AI-DLC のファイルが生まれていないことを確かめる。
2. tooling PR の小さなタスク（例: `.ignore` の作成）を、司令塔方式で 1 回動かす。
3. Claude と Codex の消費トークン、所要時間、手直しの回数を記録し、従来の方式と比べる。

### 規則

- **進行担当は 1 Intent に 1 つ**。`next` / `continue` / `report` / `park` と承認の記録は、進行担当だけが行う。
- **交代は人間が決め、区切りでだけ行う**（stage または Unit の完了時）。Unit の途中で交代しない。利用上限に達したのが Unit の途中なら、解除を待つか、人間の判断で Unit を区切りまで戻してから渡す。
- **もう一方は読み取り専用**。自分の文書（`knowledge/documents/` か scratch）だけを書く。共有の状態・監査・承認済み成果物は変更しない。
- **担当表**: `docs/ai-handoff.md`（30 行以内）を交代時だけ更新する。項目は、進行担当、交代日時、現在の stage・Unit、次の操作、所有ファイル、未解決事項。
- **並行作業**: 別の worktree で、触るファイルが重ならない作業だけにする（例: Codex が Bolt を進め、Claude が tooling PR を作る）。

## 4. 読み方の規則（両 AI 共通。AGENTS.md と .claude/CLAUDE.md に同じ文を書く）

- R1 同じ版のファイルを、1 セッションの中で読み直さない。
- R2 `audit/*.md` は通常読まない。監査の調査を頼まれたときだけ、範囲を指定して読む。
- R3 前の Intent の記録は、`next-bolt-planning-handoff.md` と本番確認メモだけを読む。
- R4 `knowledge/` 配下は、directive か stage が名指ししたものだけを読む。
- R5 テスト・ビルド・エンジンの長い出力はファイルに保存し、失敗箇所と末尾 40 行だけを文脈に入れる。
- R6 待機は完了通知か、十分に長い timeout を 1 回で行う。1〜10 秒の確認ループは使わない。
- R7（Claude）3 ファイル以上、または合計 50KB 以上の読み込みはサブエージェントに任せ、結論だけを受け取る。
- R8 ファイル全体ではなく、検索してから該当範囲を読む。

## 5. 記録の書き方

公式プロトコルが求める成果物（plan、summary、reviews、traceability、state、audit）はそのまま残す。減らすのは、それ以外に自分たちで足している分。

| 対象 | 今後の扱い | Bolt 2 の量 |
|---|---|---|
| バックアップ複製（`*.before-*`、`archive/`、`*-revision-*`） | 作らない。改訂の前に記録をコミットし、旧版はコミットから参照する（`git show <SHA>:<path>`）。承認記録から旧版を指すときはコミット SHA を書く | 49 ファイル、0.8MB → 0 |
| 一覧・照合表（inventory、matrix など） | 生成スクリプトを置き、記録には件数・ハッシュ・失敗分だけを残す | 約 0.3MB → 数 KB |
| traceability | ID の対応だけにし、証拠の本文を入れない | 0.9MB → 目安 3 割 |
| 各 Unit の `code-summary.md` | 80 行以内。決定、変更ファイル、テスト結果、未解決事項 | — |
| Intent の終了時 | `next-bolt-planning-handoff.md` を 60 行以内の索引にする（何が決まり、何が残り、どこを見ればよいか） | — |

## 6. そのほかの削減策（効果の大きい順）

自動で注入される文脈を集計した（同じ 14 セッション。2026-11-07 確認）。

| 注入の種類 | 回数 | 合計 |
|---|---:|---:|
| 公式スキル本文（`SKILL.md`、全文は 88KB ≒ 2 万トークン） | 17 | 1,216K 字 |
| セッション開始時の状態の要約（session-start hook） | 15 | 54K 字 |
| Stop hook の続きの文 | 0 | — |

**原因は人間の `$aidlc` 入力だった。** 全文（88KB）が注入された 12 回はすべて、直前に人間が `$aidlc --resume` / `$aidlc --doctor` / `$aidlc --stage …` を打っていた。Codex は `$aidlc` が入力されるたびに、すでに文脈にあってもスキル全文を入れ直す。12 回のうち 6 回はスレッドの最初の 1 回（必要な分）で、残りの 6 回は同じスレッドでの打ち直しだった。同じスレッドで 4 回打ったセッションが 2 つあり、それぞれ約 26 万字（3 回分）が重複していた。注入された分は、そのセッションのそれ以降すべての呼び出しで送り直される。Stop hook の続きの文は 1 行で `$aidlc` を含まず、今回の範囲では注入も見つからなかった（当初の「自動継続が原因」という見立ては、集計の分類の誤り）。

1. **同じスレッドで `$aidlc` を打ち直さない（最大の候補・費用ゼロ）**: `$aidlc` はスレッドの最初の 1 回だけにする。2 回目以降は「続けて」「resume」のように普通の言葉で頼む。圧縮の後で AI が手順を見失ったときだけ、もう一度 `$aidlc` を打つ。診断はターミナルで `aidlc doctor` を実行する（モデルを使わない）。Claude Code の `/aidlc` でも同じことが起きるかは未確認なので、同じ方法で確かめる。
2. **進行担当でないセッションには続きの指示を送らない**: 10/25 の文書には、調査だけのセッションに続きを促すメッセージが届いたとある。今回の範囲では再現していないので、次に起きたときに記録する。
3. **検索の対象から大きなファイルを外す**: リポジトリのルートに `.ignore` を置き、`rg` の結果から `audit/`、`archive/`、`.npm/`、画像などを除く。Git の管理には影響しない。
4. **ルールの重複を減らす**: `project.md` の Forbidden と Mandated は、同じ内容が英語と日本語で二重に入っている。memory は毎セッション読み込まれる（Claude は CLAUDE.md 経由、Codex は dispatch のときに同梱）。整理は次の Inception で learnings の儀式を通して行う。
5. **テストの出力を短くする**: Vitest は失敗だけを表示する reporter を使い、全文はファイルに保存する（R5 を具体化したもの）。
6. **やり直しの往復をなくす**: Bolt 2 では、タイミングに依存して不安定なテストのせいで U1 を何度も開き直した。不安定なテストは見つけた時点で直す。Unit と Bolt を小さく保ち、圧縮の回数を減らす。
7. **モデルの使い分け（利用枠対策）**: Claude の調査用サブエージェントは Sonnet / Haiku にする。公式の agent ごとの設定は `aidlc config models` で行う。公式レビューは省略しない。

## 7. 手元では減らせない部分

- **公式の指示文（約 7〜8 万トークン）**: セッションを細かく分けるたびに読み直しになる。逆に長いセッションでは、それまでの文脈がすべての呼び出しに乗る。目安は **1 stage（Construction では 1 Unit）につき 1 セッション**。区切りで `exit` して普通に `codex` で開き直し、最初に `$aidlc --resume` を 1 回だけ打つ（`codex resume` で前のスレッドを再開すると文脈が残る）。スキル本文 88KB は一般的なスキル（数 KB）の 10〜30 倍だが、公式 runtime は改ざん検査があり改造しない。本体の短縮と、必要な部分だけを読む形への変更を upstream に要望する。
- **hook の待ち時間**: Stop hook の約 101 秒。`.npm/u1-*`（1.8GB）を参照元を調べたうえでリポジトリ外へ移し、`AIDLC_HOOK_TRACE_DIR` で計測し直す。

## 8. 進め方（次のアプリ Bolt の前）

1. 本書の方針を人間が承認する。
2. （済 2026-11-07）スキル本文が再注入される原因を調べた（§6-1: 人間の `$aidlc` 入力）。対策は今日から運用で始められる。
3. tooling PR（例: `tooling/ai-collaboration-rules`）: AGENTS.md と `.claude/CLAUDE.md` のプロジェクト記述に §3・§4・§5 を書く。`docs/ai-handoff.md` と `.ignore` を新設する。アプリコードは変更しない。
4. `.npm/u1-*` の移動と hook の再計測（別 PR）。
5. team / project memory への恒久化と重複の整理は、次の Inception の learnings の儀式で人間の承認を得て行う。memory を直接編集しない。
6. 次の Bolt で同じ集計スクリプトを使い、Bolt 2 と比べる。
